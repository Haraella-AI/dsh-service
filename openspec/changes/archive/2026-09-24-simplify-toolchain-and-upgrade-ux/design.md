# Design

## Context

参见 proposal.md 的 Why。当前实现的三个约束决定了本方案：

- `install.sh` 以 heredoc 形式内嵌 `dshctl`，且该内嵌副本是唯一来源；安装器的选项解析与 `dshctl` 命令分发器位于同一文件中，并由同一个离线测试套件覆盖。
- 安装器按“环境变量 > 配置 > 默认值”解析生效设置，而配置中已经记录了 `DSH_SERVICE_NODE_BIN_DIR`（安装时解析出的 Node 二进制目录）。该记录值是现有安装所运行 Node 版本的唯一持久痕迹。
- `cmd_upgrade` 目前会原样解析显式目标并直接交给 `npm install -g`，因此 registry 错误会以原始 npm 输出的形式暴露。此外，当 dsh 未安装时它完全拒绝运行，这会挡住单纯的“存在哪些版本？”查询。

## Goals / Non-Goals

**目标：**

- 删除构建工具链功能，不留下任何残留代码路径、`sudo` 包管理器调用或过时文档。
- 让 Node 24 成为新安装的默认值，同时保持现有安装重新运行时的行为逐字节一致。
- 让用户能够发现存在哪些版本，并在请求的版本不存在时快速失败并给出可操作的消息——同时不使现有的安装/验证/回滚流程退化。

**非目标：**

- 不把 dsh 支持的 Node 下限提高到 22 以上，也不提示有更新版本的 Node 可用。
- 不新增配置键，也不改变优先级链。
- 不改变升级与列出版本必须复用的镜像/registry 选择逻辑。
- 不从列出的版本中进行交互式选择。

## Decisions

### 1. 删除构建工具链功能，而非将其弃用

移除 `--with-build-tools`、`WITH_BUILD_TOOLS`、`detect_pkg_manager`、`distro_name`、`ensure_build_tools`、其调用点、其摘要行及其文档。传入该标志会落入现有的未知选项路径并以 1 退出。

- 原因：该选项是安装器中唯一的发行版相关代码，也是唯一的 `sudo` 包管理器路径。若保留为被接受的空操作，就会在移除其全部价值的同时，继续保留该标志的暴露面、文档与测试。
- 考虑过的替代方案：保留该标志，打印弃用警告并以 0 退出。已否决——这会在帮助文本中留下一个死分支，并迫使未来的每一位读者都要知道该标志毫无意义。
- 后果：README 的步骤表、`--help`、安装器头部注释以及 `openspec/config.yaml` 中的项目上下文都会少一个步骤，必须重新编号；README 则保留一条简短说明，告知用户如果将来某个依赖需要编译器，应自行安装。

### 2. Node 默认 24，并配以显式的“保留已记录的 Node”规则

`NODE_MAJOR` 保持现有形态（`${OPT_NODE_MAJOR:-<default>}`），但默认值变为 24，并在 Node 准备之前先执行一个保留步骤：

- 如果传入了 `--node-major`，它无条件优先。
- 否则，如果加载的配置记录了 `DSH_SERVICE_NODE_BIN_DIR`，且其中的 `node` 可执行，则从该二进制推导主版本（`node -v`）并将其用作 `NODE_MAJOR`。
- 否则使用默认值 24。

该保留检查是只读的，因此在 `--dry-run` 下也是安全的。运行过程会报告保留了哪个版本以及如何切换（`--node-major 24` 或 `dshctl upgrade-node 24`）。

- 原因：替代方案——在所有情况下都默认 24——会让一次例行重跑下载新的 Node、重装 dsh 与 pnpm，并重写 unit，这与安装器的幂等契约以及已商定的范围决策相矛盾。
- 为什么不新增 `DSH_SERVICE_NODE_MAJOR` 配置键：Node 二进制目录已经持久化，且是权威记录；第二个键可能与它不一致。
- 考虑过的替代方案：只要记录的目录可用，就完全跳过 Node 准备。已否决——过于粗暴；它还会跳过对已记录 Node 是否仍存在的校验，并会静默忽略显式的主版本变更。推导主版本可以保持现有复用路径（在 nvm 下选择匹配的最高补丁版本）不变。
- 边界情况：较旧的配置没有记录二进制目录，或记录的目录已被删除时，会回退到 24，这正是预期的“新安装”行为。

### 3. `--list` 是只读的 registry 查询，以轻依赖方式解析实现

`cmd_upgrade` 在“dsh 未安装”检查之前识别 `--list [N]`，应用镜像设置，然后向 registry 查询版本与 dist-tag。列出路径：

- 绝不调用 `systemctl`，绝不安装，也绝不要求已安装 dsh；
- 按最新在前的顺序打印版本，并标记被某个 dist-tag 引用的版本；
- 默认使用有界数量（20），并对非数字或非正数的数量以 1 退出；
- 以网络/registry 提示报告获取失败并以 1 退出。

解析保持轻依赖：对 registry 输出进行归一化，去掉 JSON 标点并按逗号切分，然后用 `sort -V` 排序——这正是 Node 复用路径已经依赖的同一排序原语。不引入新的运行时依赖（不使用 `jq`）。

- 原因：安装器声明的依赖集合是 coreutils 加上它已经需要的工具。
- 考虑过的替代方案：用 `node -e` 解析。已否决——这会让列出路径依赖一个可用的 Node，而此时 Node 准备尚未得到验证，还会使离线桩实现复杂化。

### 4. 预校验显式目标，并区分“未找到”与“registry 无法访问”

在安装显式请求的版本或 dist-tag 之前，命令会向 registry 查询该 spec。分类比查询本身更重要：

- 版本输出非空 → 目标存在；继续。
- 输出为空且带有未找到诊断（`E404`、`ETARGET` 或 “No matching version”）→ 目标不存在。在安装前失败，并指明所请求的目标、`--list` 命令以及（尽力而为地）当前 `latest` 版本；以 1 退出。
- 任何其他失败（DNS、超时、TLS、代理）→ 无法确认是否存在。给出警告并继续进入现有的安装/验证/回滚流程。

`latest` 与省略目标的情况不受校验影响，因为解析它们本身就会查询 registry。

当 `npm install` 自身以无匹配版本的诊断失败时，会打印同一条未找到提示作为安全网，以覆盖包在校验与安装之间消失的竞态。为检测该情况，安装命令的合并输出会在仍向用户流式输出的同时，用 `tee` 捕获到已注册的临时文件；`pipefail` 保留 npm 的退出状态。

- 原因：把所有失败的查询都静默当作“版本不存在”，会在网络不稳时阻断合法的升级，这比当前原始的 npm 错误更糟。
- 考虑过的替代方案：跳过预校验，只对安装失败做模式匹配。已否决——用户明确要求在安装前就得到反馈，而预校验能在没有部分尝试安装的情况下给出干净的消息。
- 消息匹配的风险：如果某个 npm 版本重命名了其诊断信息，就会落入“无法访问”分支并仅给出警告，即退化为今天的行为，而不会造成破坏。

### 5. `upgrade` 各防护栏的顺序

`--list` 处理、显式目标校验以及现有的 `--check` 与已是最新版本的短路退出，必须按各自只在合理时才运行的顺序排列：先列出（无需 dsh 即可工作），然后是已安装版本查询，接着是目标解析与校验，再之后是已是最新版本与 `--check` 退出，最后才执行安装。这保持了 `--check` 绝不安装的当前契约。

## Risks / Trade-offs

- [在现有机器上重跑仍可能改变 Node] → 保留规则以已记录的 Node 二进制目录为依据，且测试套件断言：当记录的 Node 较旧时，第二次运行不下载任何内容并保持 unit 不变。
- [基于正则的 npm 失败分类可能误判] → 歧义一律向“继续”倾斜，因此误分类只会退化为当前行为，而不会阻断合法升级。
- [移除 `--with-build-tools` 会破坏现有脚本] → 已作为 BREAKING 记录，并在 delta 与 README 中附迁移说明；失败表现为立即、清晰的未知选项错误，而不是静默的行为变更。
- [`sort -V` 的可用性] → 这已经是 Node 复用路径的实际假设；如果排序不可用，列出命令仍必须打印出内容并以 0 退出，而不是让命令失败。
- [将 npm 安装输出捕获到文件] → 该临时文件会在现有的清理注册表中登记，因此中断的运行不会留下残留，而通过 `tee` 流式输出保持了当前的交互式输出。
- [默认 Node 24 而 doctor 接受 22] → 这是有意为之：现有安装仍然有效。README 与 `--help` 必须同时说明这两点，以免暗示 24 是必需的。
- [过时的项目上下文] → `openspec/config.yaml` 仍写着 Node 22 并称 `--with-build-tools` 是一条 `sudo` 路径；本次变更会更新它，因为未来的提案会把它当作权威上下文来读取。

## Migration Plan

无需数据或配置迁移：没有新增、删除或重命名任何配置键，现有配置文件仍然有效。

1. 将代码与文档变更一起合入，使 `--help`、README 与行为保持一致。
2. 现有安装：重新运行 `install.sh` 对 Node 而言是空操作；想要 24 的用户可执行 `dshctl upgrade-node 24` 或 `install.sh --node-major 24`。
3. 使用 `--with-build-tools` 的用户：用发行版包管理器安装编译器，然后重新运行安装器。
4. 回滚：还原该提交。本次变更触及的唯一持久状态是安装器本就会写入的 Node 二进制目录；还原即恢复先前的默认值与被移除的选项，无需任何清理。

## Open Questions

无——其余选择（默认列出数量、提示的具体措辞）都可以在不改动规范或任务分解的情况下调整。
